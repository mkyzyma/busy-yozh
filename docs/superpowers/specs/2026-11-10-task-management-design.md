# Дизайн системы управления задачами

Дата: 2026-11-10

## Назначение

Тестовое задание: разработать веб-приложение для управления задачами на Django и Django REST Framework. Результат должен демонстрировать корректную функциональность, понятную архитектуру, тесты, документацию API, оформление кода по PEP 8 и воспроизводимый запуск в Docker.

Пользователь работает с задачами через серверные HTML-страницы. Тот же набор основных операций доступен через REST API со Swagger/ReDoc и JWT-аутентификацией.

## Цели

- Создание, просмотр, редактирование и удаление задач.
- Назначение задачи существующему пользователю и смена исполнителя.
- Отметка задачи выполненной и возврат в работу.
- Просмотр и добавление комментариев к задаче.
- HTML-интерфейс и REST API без дублирования бизнес-правил.
- Регистрация и session-аутентификация в HTML, JWT access/refresh в API.
- PostgreSQL как основная база данных.
- Автоматические тесты основных сценариев, включая права доступа.
- OpenAPI-схема, Swagger UI и ReDoc.
- Запуск приложения, тестов и проверок качества через Docker Compose и Makefile.
- README с командами запуска, тестирования и примерами API.

## Не входит в объём

- SPA, React/Vue и отдельная frontend-сборка.
- OAuth 2.0, социальный вход и восстановление пароля по email.
- Роли, команды, организации и сложная система разрешений.
- Уведомления, вложения, история изменений, подзадачи и дедлайны.
- Фоновые задачи, WebSocket, кэширование и брокеры сообщений.
- Production-деплой, HTTPS, Kubernetes и инфраструктура мониторинга.

## Анти-цели

- Строгая Clean Architecture с дублированием Django ORM в отдельных доменных сущностях.
- Бизнес-логика в шаблонах, сериализаторах или разросшихся view.
- Разные правила поведения для HTML и API.
- Тесты только happy path без проверки запретов и ошибок валидации.
- Необходимость устанавливать Python или зависимости локально для обычных команд.
- Скрытые секреты в репозитории или зависимость запуска от ручных шагов, не описанных в README.

## Рассмотренные подходы

### 1. Django Templates + DRF, модульный монолит — выбран

Django Templates, Forms и session-аутентификация используются для HTML. DRF и SimpleJWT используются для API. Команды с бизнес-правилами размещаются в сервисном слое, запросы — в отдельных функциях чтения. Оба интерфейса вызывают одни и те же операции и правила авторизации.

Преимущества: минимальная инфраструктурная сложность, idiomatic Django, общая логика, простые интеграционные тесты и понятный для проверяющего код. Недостаток: границы архитектуры поддерживаются дисциплиной и тестами, а не формальными интерфейсами репозиториев.

### 2. SPA + DRF — отклонён

Дал бы независимый клиентский интерфейс, но добавил бы Node.js, frontend-зависимости, CORS, хранение JWT в браузере и отдельный контур тестирования. Это не требуется заданием и не улучшает демонстрацию Django.

### 3. Строгая Clean Architecture — отклонена

Дала бы формально независимый доменный слой, но потребовала бы собственных сущностей, маппинга ORM, интерфейсов и адаптеров репозиториев. Для небольшого CRUD-приложения это увеличивает объём кода и уменьшает пользу стандартных Django Forms, auth и ORM.

## Архитектура

Проект является модульным Django-монолитом с прагматичным разделением ответственности:

- `config` — настройки, корневые URL, WSGI/ASGI.
- `apps.accounts` — пользовательская модель, регистрация и аутентификация.
- `apps.tasks` — задачи, комментарии, бизнес-правила, HTML и API.
- `templates` — базовый шаблон и серверные страницы.
- `static` — локальный CSS без frontend-сборки.
- `tests` — unit- и HTTP integration-тесты.

Внутри `apps.tasks` технические слои являются пакетами, а файлы в них разделяются по сущностям:

```text
apps/tasks/
├── models/
│   ├── task.py
│   └── comment.py
├── services/
│   ├── task.py
│   └── comment.py
├── selectors/
│   ├── task.py
│   └── comment.py
├── rules/
│   ├── task.py
│   └── comment.py
├── forms/
│   ├── task.py
│   └── comment.py
├── views/
│   ├── task.py
│   └── comment.py
├── api/
│   ├── serializers/
│   │   ├── task.py
│   │   └── comment.py
│   ├── views/
│   │   ├── task.py
│   │   └── comment.py
│   ├── permissions/
│   │   ├── task.py
│   │   └── comment.py
│   └── urls.py
└── migrations/
```

- `models` — структура данных, связи, ограничения и простые модельные инварианты.
- `services` — команды: создание и изменение задачи, назначение исполнителя, изменение статуса, удаление, добавление комментария.
- `selectors` — queryset-функции для списков, детального представления, фильтрации и комментариев.
- `rules` — предикаты авторизации, общие для HTML и API.
- `views` — тонкие HTML-контроллеры, redirect и сообщения.
- `forms` — HTML-валидация и отображение полей.
- `api` — DRF serializers, views/viewsets, permissions и URLs, также разделённые по сущностям.

Пакеты содержат `__init__.py` с явным экспортом публичных моделей и операций. В частности, модели реэкспортируются из `models/__init__.py`, чтобы Django обнаруживал их стандартным образом. Внутренние импорты строятся от интерфейсных слоёв к services/selectors/rules и models, без циклических зависимостей.

Аналогично в `apps.accounts` модель User, формы регистрации, HTML- и API-представления разделяются по сущности. Если для небольшой операции отдельный файл избыточен, она остаётся в файле основной сущности, а не выносится в однострочный модуль ради формальной структуры.

Сервисы принимают уже валидированные данные формы или сериализатора, выполняют изменения через ORM и при необходимости `transaction.atomic()`. Правила доступа проверяются до выполнения команды общими предикатами; DRF преобразует отказ в 403, HTML — в 403 или понятное сообщение без изменения данных. Чтение выполняется через selectors с `select_related`/`prefetch_related` там, где это нужно.

Полноценный слой репозиториев, собственные доменные сущности и Unit of Work не добавляются: Django ORM уже выполняет эту инфраструктурную роль в выбранном масштабе.

## Пользователи и аутентификация

С самого начала используется пользовательская модель `User` на базе `AbstractUser` с обычным username. Это сохраняет стандартное поведение Django и позволяет изменить модель позже без болезненной миграции.

- HTML: регистрация, вход, выход, Django sessions, CSRF для всех изменяющих запросов.
- API: получение и обновление JWT через SimpleJWT.
- Все операции с задачами требуют аутентификации.
- Список пользователей для назначения доступен аутентифицированным пользователям и содержит только публичные поля `id` и `username`.
- Регистрация доступна в HTML; создание пользователей также возможно через админку и `createsuperuser`. Отдельный API регистрации не требуется заданием.

## Модель данных

### User

Стандартные поля `AbstractUser`. Самостоятельных чувствительных данных в API не раскрывать.

### Task

- `id`.
- `title` — обязательная строка с ограничением длины.
- `description` — необязательный текст.
- `author` — FK на User, создатель задачи.
- `assignee` — nullable FK на User, исполнитель.
- `is_completed` — boolean, по умолчанию false.
- `created_at`, `updated_at`.

Автор устанавливается текущим пользователем и не передаётся клиентом как свободно изменяемое поле. Исполнителя можно не указывать, назначить при создании/редактировании или снять. Индексы добавляются для фильтрации по исполнителю, автору и статусу. Удаление автора удаляет его задачи; удаление исполнителя обнуляет назначение.

### Comment

- `id`.
- `task` — FK на Task.
- `author` — FK на User.
- `text` — обязательный непустой текст.
- `created_at`.

Комментарии создаются и просматриваются; редактирование и удаление комментариев не добавляются, поскольку этого нет в задании.

## Правила доступа

- Аутентифицированный пользователь видит список всех задач и их комментарии.
- Любой аутентифицированный пользователь может создать задачу.
- Только автор задачи может редактировать её поля, назначать/снимать исполнителя и удалять задачу.
- Автор или назначенный исполнитель может отметить задачу выполненной или вернуть её в работу.
- Любой аутентифицированный пользователь может комментировать задачу.
- Назначение возможно только на существующего пользователя; исполнитель не обязан отличаться от автора.
- Неавторизованные HTML-запросы перенаправляются на вход; API возвращает 401.
- Запрещённые действия возвращают 403, отсутствующие объекты — 404.

Правила явно документируются в README и проверяются тестами от имени автора, исполнителя и постороннего пользователя.

## HTML-интерфейс

Страницы:

- Регистрация, вход и выход.
- Список задач с пагинацией и фильтрами «все», «мои», «назначенные мне», «в работе», «выполненные».
- Создание задачи.
- Детальная страница: поля задачи, автор, исполнитель, статус, комментарии и форма комментария.
- Редактирование задачи, включая исполнителя.
- Подтверждение удаления.
- POST-действие переключения статуса.

Изменяющие действия выполняются только POST-запросами. После успешной обработки используется Post/Redirect/Get и Django messages. Кнопки недоступных действий не показываются, но серверные проверки остаются обязательными.

Оформление — адаптивные Django Templates и небольшой локальный CSS, без CDN и JavaScript-зависимостей. Интерфейс должен быть аккуратным и удобным для демонстрации, но сложный дизайн не является целью.

## REST API

Базовый префикс: `/api/v1/`.

- `POST /auth/token/` — получение access/refresh JWT.
- `POST /auth/token/refresh/` — обновление access token.
- `GET /users/` — список пользователей для назначения.
- `GET, POST /tasks/` — список и создание задач.
- `GET, PATCH, PUT, DELETE /tasks/{id}/` — просмотр и изменение задачи.
- `POST /tasks/{id}/completion/` — переключение статуса; желаемое состояние передаётся явно как `is_completed`.
- `GET, POST /tasks/{id}/comments/` — список и добавление комментариев.

Список задач поддерживает пагинацию и query-фильтры по автору, исполнителю и статусу. Вложенные комментарии в объект задачи не включаются, чтобы не создавать лишние запросы и дублировать API.

Serializer валидирует входные данные и не разрешает клиенту менять автора. Ответы используют стандартные коды DRF: 200/201/204, 400, 401, 403, 404. Ошибки валидации возвращаются в едином DRF-формате.

Документация генерируется через drf-spectacular:

- `/api/schema/` — OpenAPI schema.
- `/api/docs/swagger/` — Swagger UI.
- `/api/docs/redoc/` — ReDoc.

## Конфигурация и Docker

- Python и стабильные совместимые версии Django/DRF фиксируются через Poetry и lock-файл при реализации.
- Настройки читаются из переменных окружения; `.env.example` содержит только безопасные демонстрационные значения.
- PostgreSQL запускается отдельным контейнером с healthcheck и volume.
- Dockerfile устанавливает зависимости и запускает Django; Compose связывает приложение и БД.
- Development Compose включает монтирование исходников и autoreload.
- При старте приложения выполняются миграции; ожидание готовности БД обеспечивается healthcheck/entrypoint.
- Тесты создают отдельную тестовую БД и не используют данные разработки.
- Для обычной разработки не требуются локальные Poetry, Python или Node.js.

Makefile сохраняет стиль референса `platform-backend/Makefile`, но без NATS, Qdrant, MinIO, Alembic и TLS. Основные команды:

- `make help`, `make dev`, `make dev-build`, `make dev-stop`, `make dev-clear`.
- `make migrate`, `make migration name="..."`, `make createsuperuser`, `make shell`.
- `make test`, `make test-cov`.
- `make lint`, `make format`, `make typecheck`, `make check`.
- `make clean`.

Все project-specific команды выполняются в одноразовом приложении-контейнере через `docker compose run --rm`, кроме запуска постоянных сервисов и локального удаления кэшей.

## Тестирование

Используются pytest, pytest-django и DRF APIClient. Тестовые данные создаются через фабрики без зависимости от фиксированного порядка тестов.

Покрытие по поведению:

- Модели и ограничения: обязательные поля, связи, значения по умолчанию.
- Сервисы: создание, редактирование, назначение, статус и комментарий.
- HTML: регистрация/вход, CRUD, фильтры, назначение, статус, комментарии, POST/CSRF и запреты.
- API: весь CRUD, назначение, статус, комментарии, валидация, пагинация и коды ошибок.
- JWT: доступ без token, получение token, доступ с token и refresh.
- Права: автор, исполнитель, посторонний пользователь и аноним.
- OpenAPI: схема и страницы документации доступны, основные endpoints присутствуют.

Основные пользовательские сценарии проверяются end-to-end через Django test client и DRF APIClient против реальной тестовой PostgreSQL, а не только вызовами функций. Coverage настраивается для кода приложений с порогом 85%, но обязательные поведенческие тесты важнее процента.

Проверки качества:

- Ruff check и Ruff format для PEP 8, импортов и стандартных ошибок.
- mypy с django-stubs для типизации основного кода.
- `manage.py check` и `makemigrations --check --dry-run`.
- pytest и coverage.
- GitHub Actions повторяет lint, typecheck, тесты и Docker build.
